# Among_Us_IRL
An in-real-life simulation of the game "Among Us," built on a Node.js server-client relationship.

## How it's done
You'll need **3 devices** acting as servers on the local network:
- 1 for reactor sabotage handling
- 1 for oxygen
- 1 for the actual server logic

Every player needs a mobile device to carry around and complete tasks on.

## Requirements
- [Node.js](https://nodejs.org/) (LTS version recommended)
- npm (comes bundled with Node.js)
- All devices connected to the same local network (unless using one of the remote-access methods below)

## Setup (required no matter which hosting method you pick)

Every method below needs the server to know its IP, port, protocol, and password hash — that all comes from a single `.env` file. Do this step first, regardless of how you end up running the server.

- Download the project and run `npm install`.
- Create a `.env` file at the project root:

```
PORT = {your port}
IP = {your device ip}
PROTOCOL = "http"
PASSWORD_HASH = {your password hash}
```

- Set `IP` to your device's IP address.
- Set `PORT` to some high 4-digit number, e.g. `8812` or `9432`.
- Leave `PROTOCOL` as `"http"` unless you're hosting behind a real TLS certificate (see the reverse-tunnel method below).
- Set `PASSWORD_HASH` to the hash generated by **bcrypt** at **10 salt rounds**.

The `.env` file must sit in the same working directory the server process is launched from — this matters most for the Docker, systemd, and Windows service methods below, where "working directory" isn't automatically the project folder unless you set it explicitly.

## Firewall rules (needed for LAN hosting)

By default, most OS firewalls block unsolicited inbound connections — so even with the server running and `.env` configured correctly, other devices on the same Wi-Fi may not be able to reach it until you open the port. This applies to methods 1–5 below; it's **not** needed for the tunnel method, since ngrok/Cloudflare Tunnel/localtunnel establish an outbound connection and handle inbound traffic themselves.

**Windows** (run in an elevated PowerShell/Command Prompt):
```powershell
netsh advfirewall firewall add rule name="Among Us IRL" dir=in action=allow protocol=TCP localport={your port}
```

**macOS**:
```bash
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add /usr/local/bin/node
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --unblockapp /usr/local/bin/node
```
(Adjust the path if `which node` points somewhere else, e.g. `/opt/homebrew/bin/node` on Apple Silicon.)

**Linux (ufw)**:
```bash
sudo ufw allow {your port}/tcp
```

**Linux (firewalld)**:
```bash
sudo firewall-cmd --add-port={your port}/tcp --permanent
sudo firewall-cmd --reload
```

If you're using Docker with the default bridge network (not `network_mode: host`), the Docker daemon manages its own iptables rules for the published port — but the host firewall rule above is usually still required on top of that, since ufw/firewalld can override or coexist awkwardly with Docker's rules depending on distro defaults. If players still can't connect after publishing the port, check the host firewall first.

## How do I play
With `.env` in place, host it. There are a few ways to do this — pick whichever fits your setup.

### 1. Node.js directly (recommended)

Start the server with `npm start` (or `node index.js`, depending on your `package.json`), run from the project root so it picks up `.env` automatically.

This is the simplest option and is best if everyone is going to be on the same Wi-Fi network.

### 2. PM2 (keep the server alive)

If you want the server to auto-restart on crashes or reboots (handy for longer game sessions), use [PM2](https://pm2.keymetrics.io/):

Run this from the project root (same folder as your `.env`) so PM2's spawned process inherits it the same way `npm start` would:

```bash
npm install -g pm2
pm2 start npm --name "among-us-irl" -- start
pm2 save
```

Useful commands:
```bash
pm2 logs among-us-irl   # view live logs
pm2 restart among-us-irl
pm2 stop among-us-irl
```

### 3. Docker

If you'd rather not install Node directly on the host device, containerize it:

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
CMD ["npm", "start"]
```

Build and run:
```bash
docker build -t among-us-irl .
docker run -d --env-file .env -p {your port}:{your port} among-us-irl
```

Or with `docker-compose.yml`:
```yaml
services:
  among-us-irl:
    build: .
    env_file: .env
    ports:
      - "{your port}:{your port}"
    restart: unless-stopped
```
```bash
docker compose up -d
```

> **Note:** if the server binds directly to the `IP` value from `.env` (rather than `0.0.0.0`), default Docker bridge networking won't have that address on its interface and the bind will fail. Either add `network_mode: host` (Linux only) to `docker-compose.yml`, or check whether the app can bind to `0.0.0.0` while still advertising your LAN `IP` to clients.

### 4. Linux systemd service

To run the server as a background service that survives reboots:

```ini
# /etc/systemd/system/among-us-irl.service
[Unit]
Description=Among Us IRL Server
After=network.target

[Service]
WorkingDirectory=/path/to/Among_Us_IRL
ExecStart=/usr/bin/npm start
Restart=always
User=your-username
EnvironmentFile=/path/to/Among_Us_IRL/.env

[Install]
WantedBy=multi-user.target
```

`EnvironmentFile` is what actually loads `.env` here — systemd doesn't read files named `.env` on its own, so this line is required even though `WorkingDirectory` also points at the same folder.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now among-us-irl
```

### 5. Windows Service

On Windows, use [NSSM](https://nssm.cc/) to run the server as a service instead of a terminal window:

```powershell
nssm install AmongUsIRL "C:\Program Files\nodejs\node.exe" "C:\path\to\Among_Us_IRL\index.js"
nssm set AmongUsIRL AppDirectory "C:\path\to\Among_Us_IRL"
nssm start AmongUsIRL
```

The `AppDirectory` line matters: NSSM doesn't default the working directory to your project folder, and without it the process won't find `.env` sitting next to `index.js`.

### 6. Playing across separate networks (advanced, riskier)

The server is meant for **localhost / same-LAN use only**. If some players aren't on your Wi-Fi, you can expose it with a tunneling tool instead of opening ports on your router:

- **[ngrok](https://ngrok.com/)**: `ngrok http {your port}` — gives you a temporary public HTTPS URL that forwards to your local server.
- **[Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/)**: `cloudflared tunnel --url http://localhost:{your port}` — similar idea, no account strictly required for a quick tunnel.
- **[localtunnel](https://github.com/localtunnel/localtunnel)**: `npx localtunnel --port {your port}` — lightweight npm-based alternative.

> ⚠️ **This significantly increases the security risk described below.** Exposing the server to the public internet, even briefly, means anyone who finds the URL can interact with it — not just your players. Only use this for the duration of a single game session, and shut the tunnel down immediately afterward.

## Important security note
This server is meant to be hosted on **localhost only**. Several serious vulnerabilities are present intentionally, because I didnt bother to fix them. (It aint like im building this for a megacorporation or something)

The client is **completely trusted** (well, mostly), so if you play this game, keep in mind that anyone with decent cybersecurity skills can cheat  though they'd need external tools that aren't easily obtainable on mobile. This risk is much higher if you use one of the remote-access methods above, since the server is no longer confined to your local network.
