# Among_Us_IRL
An in-real-life simulation of the game "Among Us," built on a Node.js server-client relationship.

## How it's done
You'll need **3 devices** acting as servers on the local network:
- 1 for reactor sabotage handling
- 1 for oxygen
- 1 for the actual server logic

Every player needs a mobile device to carry around and complete tasks on.


## Requirements
- [Node.js](https://nodejs.org/) (LTS version recommended)
- npm (comes bundled with Node.js)
- All devices connected to the same local network (unless using one of the remote-access methods below)

## Setup (required no matter which hosting method you pick)

Every method below needs the server to know its IP, port, protocol, and password hash - that all comes from a single `.env` file. Do this step first, regardless of how you end up running the server.

- Download the project and run `npm install`.
- Create a `.env` file at the project root:

```
PORT = {your port}
IP = {your device ip}
PROTOCOL = "http"
PASSWORD_HASH = {your password hash}
```

- Set `IP` to your device's IP address.
- Set `PORT` to some high 4-digit number, e.g. `8812` or `9432`.
- Leave `PROTOCOL` as `"http"` unless you're hosting behind a real TLS certificate (see the reverse-tunnel method below).
- Set `PASSWORD_HASH` to the hash generated by **bcrypt** at **10 salt rounds**.


The `.env` file must sit in the same working directory the server process is launched from - this matters most for the Docker, systemd, and Windows service methods below, where "working directory" isn't automatically the project folder unless you set it explicitly.

#### Bcrypt

To get the 10 salt round hash, uncomment from line **36 to 41**, you will get your hash in the **console**

Dont forget to comment the code snippet again (or delete it), since it **halts** the script purposefully.


## Firewall rules (needed for LAN hosting)

By default, most OS firewalls block unsolicited inbound connections - so even with the server running and `.env` configured correctly, other devices on the same Wi-Fi may not be able to reach it until you open the port. This applies to methods 1–5 below; it's **not** needed for the tunnel method, since ngrok/Cloudflare Tunnel/localtunnel establish an outbound connection and handle inbound traffic themselves.

**Windows** (run in an elevated PowerShell/Command Prompt):
```powershell
netsh advfirewall firewall add rule name="Among Us IRL" dir=in action=allow protocol=TCP localport={your port}
```

**macOS**:
```bash
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --add /usr/local/bin/node
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --unblockapp /usr/local/bin/node
```
(Adjust the path if `which node` points somewhere else, e.g. `/opt/homebrew/bin/node` on Apple Silicon.)

**Linux (ufw)**:
```bash
sudo ufw allow {your port}/tcp
```

**Linux (firewalld)**:
```bash
sudo firewall-cmd --add-port={your port}/tcp --permanent
sudo firewall-cmd --reload
```

If you're using Docker with the default bridge network (not `network_mode: host`), the Docker daemon manages its own iptables rules for the published port - but the host firewall rule above is usually still required on top of that, since ufw/firewalld can override or coexist awkwardly with Docker's rules depending on distro defaults. If players still can't connect after publishing the port, check the host firewall first.

## How do I play
With `.env` in place, host it. There are a few ways to do this. pick whichever fits your setup.

### 1. Node.js directly (recommended)

Start the server with `npm start` (or `node index.js`, depending on your `package.json`), run from the project root so it picks up `.env` automatically.

This is the simplest option and is best if everyone is going to be on the same Wi-Fi network.

### 2. PM2 (keep the server alive)

If you want the server to auto-restart on crashes or reboots (handy for longer game sessions), use [PM2](https://pm2.keymetrics.io/):

Run this from the project root (same folder as your `.env`) so PM2's spawned process inherits it the same way `npm start` would:

```bash
npm install -g pm2
pm2 start npm --name "among-us-irl" -- start
pm2 save
```

Useful commands:
```bash
pm2 logs among-us-irl   # view live logs
pm2 restart among-us-irl
pm2 stop among-us-irl
```

### 3. Docker

If you'd rather not install Node directly on the host device, containerize it:

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
CMD ["npm", "start"]
```

Build and run:
```bash
docker build -t among-us-irl .
docker run -d --env-file .env -p {your port}:{your port} among-us-irl
```

Or with `docker-compose.yml`:
```yaml
services:
  among-us-irl:
    build: .
    env_file: .env
    ports:
      - "{your port}:{your port}"
    restart: unless-stopped
```
```bash
docker compose up -d
```

> **Note:** if the server binds directly to the `IP` value from `.env` (rather than `0.0.0.0`), default Docker bridge networking won't have that address on its interface and the bind will fail. Either add `network_mode: host` (Linux only) to `docker-compose.yml`, or check whether the app can bind to `0.0.0.0` while still advertising your LAN `IP` to clients.

### 4. Linux systemd service

To run the server as a background service that survives reboots:

```ini
# /etc/systemd/system/among-us-irl.service
[Unit]
Description=Among Us IRL Server
After=network.target

[Service]
WorkingDirectory=/path/to/Among_Us_IRL
ExecStart=/usr/bin/npm start
Restart=always
User=your-username
EnvironmentFile=/path/to/Among_Us_IRL/.env

[Install]
WantedBy=multi-user.target
```

`EnvironmentFile` is what actually loads `.env` here - systemd doesn't read files named `.env` on its own, so this line is required even though `WorkingDirectory` also points at the same folder.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now among-us-irl
```

### 5. Windows Service

On Windows, use [NSSM](https://nssm.cc/) to run the server as a service instead of a terminal window:

```powershell
nssm install AmongUsIRL "C:\Program Files\nodejs\node.exe" "C:\path\to\Among_Us_IRL\index.js"
nssm set AmongUsIRL AppDirectory "C:\path\to\Among_Us_IRL"
nssm start AmongUsIRL
```

The `AppDirectory` line matters: NSSM doesn't default the working directory to your project folder, and without it the process won't find `.env` sitting next to `index.js`.

### 6. Playing across separate networks (advanced, riskier)

The server is meant for **localhost / same-LAN use only**. If some players aren't on your Wi-Fi, you can expose it with a tunneling tool instead of opening ports on your router:

- **[ngrok](https://ngrok.com/)**: `ngrok http {your port}` - gives you a temporary public HTTPS URL that forwards to your local server.
- **[Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/)**: `cloudflared tunnel --url http://localhost:{your port}` - similar idea, no account strictly required for a quick tunnel.
- **[localtunnel](https://github.com/localtunnel/localtunnel)**: `npx localtunnel --port {your port}` - lightweight npm-based alternative.

> **This significantly increases the security risk described below.** Exposing the server to the public internet, even briefly, means anyone who finds the URL can interact with it - not just your players. Only use this for the duration of a single game session, and shut the tunnel down immediately afterward.

### 1. Host

- Instead of logging in normally, click the **"I am host"** link below
- Enter your password (the one you got from the bcrypt step)
- Done


### 2. Server setup

- Instead of logging in normally, click the **"I am host"** link below

## Tasks

Tasks are QR codes placed around the play area; the server accepts or declines each scan.

Every `.html` file in the `minigames/` folder is a task, and its file name is the `task.id`. There is no import step: add, rename or delete a file and the task list changes.

`tasks.json` switches each task on or off, sets its location and how many QR codes it has (`tasks`: `"repeat": 3` makes one task out of three codes done in order), and chains tasks into one (`binds`, e.g. `"refuel_tank": "fuel_engine"`: the second appears once the first is done). A task with an empty location uses the `<meta name="location">` in its minigame instead. The server warns at startup how many tasks have no location in `tasks.json`.

Each task is scanned through a random secret token. The server creates tokens by itself and saves them in `tokens.json`, so printed QR codes keep working across restarts. The links are written to `tasks.txt` (each task's id, then its link on the next line) - make QR codes from those.

```bash
npm run task-links           # show the links (the server already keeps tasks.txt up to date)
npm run task-links -- --new  # issue new tokens for every task (old QR codes stop working)
```

At game start every player gets `tasks` random tasks (set in the host lobby) and sees them on a sticky note next to their tablet. Impostors get tasks too, but those don't count towards the crew total. More details: `/help?topic=tasks`.

> Players must scan with the same browser they joined with (login is a cookie), and the links use `IP`/`PORT` from `.env`, so run `npm run task-links -- --new` (or delete `tokens.json` and restart) if those change.

## Floor plan

In the host lobby, **Floor plan** opens the editor (host only). Draw each floor with walls and doors, name every room, and drag every task into the room where its QR code hangs. Saving checks the plan and writes it to `map/map.json`; it also updates `tasks.json`: tasks placed on the plan are switched on with their room as location, tasks left off are switched off.

- Every line end must touch another line (its end or anywhere along it).
- A door sits in a gap between walls: each door end touches exactly one wall, and nothing touches a door's middle. Drawing a door along a wall cuts that part of the wall out for you.
- The eraser removes the piece of a line between two junctions; a wall with exactly one connected end can be rotated around that end.
- Every enclosed area is a room and needs a unique name; all rooms on a floor must be reachable through doors.
- A bound or repeating task must have all its parts placed, or none.
- A reference image (a photo or drawing of the plan) can be traced over; it is only shown in the editor.
- The editor won't save while a game is running.
- **Export** saves the plan (with its reference images) to a `.json` file; **Import** loads one back, e.g. on another server or as a backup. An import is only kept once you save.

`npm run verify:floorplan` checks the rules on sample plans.

## Tablet map

Once a floor plan is saved, every player's tablet gets a **Map** button (the impostor remote too). The tablet's screen turns into the map and then grows to fill the phone; the back button, the arrow or Escape close it again.

- It shows only what the player needs: the next step of each of their own tasks (the second part of a bound task appears once the first is done), with a count per floor on the floor tabs.
- Tap a pin for its name and room; pinch, drag and double-tap to zoom; the corner button fits the whole floor again.
- **Done** shows finished tasks too; a teal ring marks where the player last scanned a task.
- The emergency button is always shown; O2 and reactor light up while they are sabotaged (place these "stations" in the floor plan editor's Tasks tab).
- On the sticky note, the pin next to a task opens the map right on it.

Where each QR code is gets fixed when the game starts, so editing the plan mid-game doesn't move anyone's pins.

## Meetings

When the emergency button is pressed, or someone reports a body, every player's tablet (crewmates and impostors alike) turns into a full-screen alert telling everyone to go to the emergency room, with an **I'm present** button underneath. The meeting itself, and its voting countdown, only starts once every living player has tapped it.

- The alert shows who has checked in so far, and the emergency station shows the same count and who it's still waiting for.
- Tapping **I'm present** in the first 10 seconds after the call asks first: it explains that the button means you are standing in the emergency room, and asks whether you really are.
- Ghosts (dead players) don't check in and aren't counted. If a player logs out while everyone is gathering, the meeting stops waiting for them.
- No one can die once a meeting is called: "I'm dead" is refused until the meeting is over. No tasks or sabotage either, and sabotage countdowns stay paused.
- The host's alert also has **Host: start the meeting now**, which starts the meeting without waiting for the rest (it asks first).
- The station set to play the meeting call (the emergency station, out of the box) plays the alarm (`public/sounds/meeting.mp3`, repeating) and the voice says *"Emergency meeting. All personnel: remain calm. Gather in the emergency room."*, or for a body, *"Dead body was found. Emergency meeting. ..."*. Every 20 seconds until everyone is there it says how many are present and how many it's still waiting for. The lines are made on the fly by the same voice as the O2 and reactor alarms, and are set in `voice.json` under `meeting` (see below). The alarm and the voice stop the moment the meeting begins.

## Alarm voice

When the O2 or reactor alarm goes off, its station plays the alarm sound (`public/sounds/o2.mp3`, `public/sounds/reactor.mp3`) and a voice names a random section of the ship, for example *"Warning! Reactor section 4B is unstable. Meltdown in 1 minute 30 seconds."* It counts down while the alarm runs and reads out how the repair is going (*"1 override lever pushed... 2 needed for an override."*, *"0 codes provided... 2 are needed for an override."*), both in the countdown lines and whenever a code goes in or a lever is pushed or let go. Once the crew fixes it, it names the same section again: *"Reactor section 4B stable."*

- The voice is made on the server, offline, with [Piper](https://github.com/rhasspy/piper) (the Lessac voice) through `sherpa-onnx-node`. A line takes a fraction of a second on a desktop processor.
- The voice (about 80 MB) is downloaded once from GitHub, the first time the server starts, into `voice/models/`. Without internet at that moment, or on a system it can't run on (Alpine Linux in Docker, for example), the alarms play without the voice and the reason is in `error.log`.
- The station mixes the alarm and the voice in its browser, with reverb over both. Press **Connect** on the station so the browser allows sound.
- When the game ends, the crewmate or impostor win sound plays (`public/sounds/win_crewmates.mp3`, `public/sounds/win_impostors.mp3`). If the station is still speaking (*"Containment lost."*), the sound starts once the line is over.

### Station sounds

In the host lobby, **Station sounds** lists the four stations (O2, reactor, emergency, communications) and whether a device is connected to each. Tick what each one plays: the O2 alarm, the reactor alarm, the crewmate win, the impostor win, the meeting call (see [Meetings](#meetings)) and the communications error (*"Attention, critical error in communications..."*, played once when communications go down; once they're back, the same stations say *"Attention! Communications restored."*, `public/sounds/communications_restored.mp3`). More than one station can play the same sound, and one station can play several, so the alarm can sound in more than one room. An alarm's spoken lines play wherever that alarm plays.

- Out of the box, the O2 station plays the O2 alarm, the reactor station plays the reactor alarm and both win sounds, and the communications station plays the communications error. The emergency station plays the meeting call.
- The choice is saved in `sounds.json` next to `server.js`, by station, so it stays through a reset, a server restart and a device swap. Changes apply straight away, even during an alarm.
- The emergency station has no Connect button, so if its browser holds the sound back it shows **Tap to enable sound** until someone taps the screen (only while it has sounds to play).

Everything is set in `voice.json` next to `server.js`. It is read each time an alarm starts, so changes apply to the next alarm without a restart. Leave a key out (or delete the file) and the default is used.

| Key | What it does |
|---|---|
| `enabled` | `false` turns the voice off; the alarm sound still plays. |
| `voice.model`, `voice.speaker`, `voice.speed` | Which Piper voice, which speaker in it, and how fast it talks (1 = normal). Any `vits-piper-*` voice from the [sherpa-onnx tts-models release](https://github.com/k2-fsa/sherpa-onnx/releases/tag/tts-models) works and is downloaded on first use. |
| `voice.pause` | Extra seconds of silence for each `...` in a line (see below). |
| `schedule.every` | Seconds between countdown lines. |
| `schedule.finalFrom`, `schedule.finalEvery` | From this many seconds left, speak a short line every `finalEvery` seconds. A line is skipped while the previous one is still playing. |
| `schedule.statusDelay` | Seconds to wait after the repair changes before reading out the status, so a lever pushed and let go quickly is read out once. It also waits for the voice to be free. |
| `audio.alarmVolume`, `audio.voiceVolume` | 0 to 1. |
| `meeting.button`, `meeting.report` | What the meeting call says when the button is pressed, or a body is reported. |
| `meeting.attendance`, `meeting.every` | The line saying who's in the emergency room ({present}, {waiting} still to come, {total} expected), and how many seconds apart. |
| `meeting.loop` | `true` (the default) repeats the meeting alarm until the meeting begins; `false` plays it once. |
| `audio.duckTo` | How loud the alarm stays while the voice speaks (0.35 = 35%). The meeting call only drops to 0.7. |
| `audio.winVolume` | How loud the end-of-game sound is, 0 to 1. |
| `audio.announceVolume` | How loud the communications announcements are, 0 to 1. |
| `audio.reverb.mix`, `.seconds`, `.decay` | How much reverb, how long it rings, and how fast it fades (higher decay = smaller room). `o2.audio` and `reactor.audio` override these per station; O2 gets less by default because its sound already has reverb. |
| `sections` | Patterns for the section an alarm names: `#` becomes a random digit, `@` a random letter (never I or O). `"#@"` gives sections like 4B. `o2.sections` or `reactor.sections` override it for one station. |
| `start`, `countdown`, `final`, `fixed`, `failed` | The lines (under `o2` and `reactor`). One is picked at random each time. They can use `{section}`, `{time}` (time left in words), `{seconds}` and `{status}` (the status line below). |
| `status`, `ready` | How the repair is going: `{count}` codes or levers so far, `{need}` how many it takes, and `{s}` (an "s" unless the count is 1, for "1 code" / "0 codes"). `ready` is used instead once there are enough (the reactor's levers are all pushed). |
| `o2.alarm`, `reactor.alarm` | The alarm sound each station loops. |

**Pauses:** Piper barely pauses at commas or full stops, so `...` is a real pause: the line is spoken in pieces with `voice.pause` seconds of silence between them, like the gap before the number in a station announcement: `"Meltdown in... {time}."` → *"Meltdown in — 1 minute 30 seconds."*

## Testing minigames

In the host lobby, **Test minigames** opens a test bench (host only): every minigame in `minigames/` (and any `_draft` files) can be played in a phone, sideways phone or tablet sized frame, with a timer and a "finished" signal. Nothing is recorded in a game, and `fuel_engine` gets a pretend tank you can set to full or empty. Mark each one "Works" or "Has a problem" with a note; the marks are kept in that browser.

## Important security note
This server is meant to be hosted on **localhost only**. Several serious vulnerabilities are present intentionally, because I didnt bother to fix them. (It aint like im building this for a megacorporation or something)

The client is **completely trusted** (well, mostly), so if you play this game, keep in mind that anyone with decent cybersecurity skills can cheat. (though they'd need external tools that aren't easily obtainable on mobile) This risk is much higher if you use one of the remote-access methods above, since the server is no longer confined to your local network.
